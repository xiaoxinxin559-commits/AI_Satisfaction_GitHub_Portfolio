# AI Agent 协作的满意度分析与可视化交付

> 工作经历部分依据作者提供的 Agent 过程记录归纳。为保护业务与用户信息，不公开产品名、真实数值、原始字段表或内部链接。代码、网页、图表、Skill 文本与合成数据是本次作品整理新增内容。

## 1. 背景与目标

在对话式 AI 产品的满意度专项中，团队同时拥有用户评分、交互行为、功能使用记录、反馈标签与独立评测。仅看总体满意率难以解释用户体验，也无法保证产品内容达到专业质量要求。

我将任务拆成三条线：明确行为指标与评分之间的关联；定位用户主观评价与独立评测的差异；把指标取舍、分析结果与后续建议交付成可复核的报告及交互页面。

这是一项分析与诊断任务，不把观察性相关直接当成因果效果，也不把产品后续变化自动归因于本次分析。

## 2. 选择工具的理由

历史工作使用企业内部的数据分析 Agent，配合 Python 执行、分析 Skill 与知识库可视化组件。选择它的理由是与当时已有的数据分析和交付环境衔接，能在授权环境中完成代码执行和文档整理，而不是未经验证地声称它优于所有模型。

记录没有给出可确认的底层模型版本，因此本项目不填写 GPT、Claude 等具体版本，也不将其他个人工具经验嫁接到这一项目。公开作品使用 Python、SQLite 与离线 HTML 重建方法示例，不连接原平台。

## 3. 人与 AI 的分工

| 阶段 | 我负责 | AI 辅助 |
|---|---|---|
| 明确问题 | 区分解释满意度、预测评分和解释下游行为等不同目标 | 整理任务、生成可讨论的分析方案 |
| 确认口径 | 明确评分尺度、事件定义、样本单元、匿名标识与问卷跳转规则 | 输出字段分布、缺失率、异常值及待确认清单 |
| 建模比较 | 选择与变量类型匹配的方法，判断变量是前因、同源标签还是下游结果 | 编写与运行统计代码，输出拟合与诊断表 |
| 结果审查 | 质疑符号反转、高相关指标、无法追溯的数值及不合理结论 | 回到数据复算，做条件与边际关联、分层及敏感性对照 |
| 解释与交付 | 明确哪些结论成立、哪些只是待验证假设，确认发布范围 | 整理报告、交互看板、方法附录与可复用的流程文本 |

AI 是执行与整理助手；方法选择、结果验收和对外结论由我负责。

## 4. 工作链路

### 口径审计：先问数据代表什么

先明确一条记录究竟是一名用户、一次会话还是一次问卷。对匿名标识不能按统一的 `0` 值合并用户。对空列、常量列、多值类别和系统改版字段逐一交代去向，避免只检查数值字段。

公开演示新增了会话去重、全字段审计与 SQL 时序检查。它们展示同类质量控制思路，不意味着历史流程已经使用了这些新脚本。

### 模型选择：先问变量在什么时候产生

评分之后才展示的标签不能被当作评分的先验解释；同期订单等下游结果也不能因为相关性高就自动进入前因模型。连续近似、二元、有序结果的模型路线分别讨论。

历史记录涉及 SEM 及其多轮规格调整。公开代码不补造缺失的 SEM 模型文件，而采用透明的回归与有序模型演示，明确保留差异。

### 人工复核：不把“AI 跑完了”当成完成

对每个异常结果先检查字段定义、软件默认设置、相关矩阵、变量共线性和参数是否真的受到约束。对看似更高的解释度，检查它是否依赖评分门控标签或改变了解释目标。

### 反馈交叉：满意并不等于所有质量要求都通过

把用户评分与独立评测按各自明确阈值交叉，优先审查相互背离的样本。用户评价反映感知体验，评测反映特定标准下的质量判断；两者都存在测量误差，不能把任何一方直接宣称为无误的真值。

### 可视化交付：让同事能追到依据

将指标纳入/排除依据、诊断结果、反馈问题和建议整理为知识库报告及可搜索、筛选、排序的交互看板。流程稳定后，沉淀为可重复使用的 Skill / prompt，并保留模型取舍和数值复核记录。

## 5. 关键困难与解决思路

| 困难 | 处理 | 价值 |
|---|---|---|
| 相同名称对应不同变量形态 | 先确认评分、满意率、二元订单与真实计数的定义 | 避免选错结果模型 |
| 标签与评分高度相关 | 检查标签是否由评分分支决定 | 防止把问卷规则当成产品规律 |
| 模型系数出现反向 | 核对指标、时序、相关结构及条件效应 | 不急于把异常符号翻译成产品建议 |
| 测量模型多次失败 | 审查识别、载荷与残差，必要时回到显变量模型 | 不为保留复杂方法牺牲可解释性 |
| 新旧数据或报告数字不一致 | 锁定样本、字段、预处理、相关矩阵与估计方法 | 让每个正式结论都有版本依据 |
| 报告难以查阅 | 做成指标台账与交互页面 | 让字段取舍和结论可追溯 |

## 6. 结论与建议如何表达

历史工作形成了围绕推荐匹配、事实准确性、重复追问与服务交付体验的排查方向。公开作品不披露真实排名或系数，也不把观察性关联改写成已实现的提升。

建议按“问题证据 → 可改变的产品动作 → 验证方式”连接：例如，针对无效或重复追问先检查样本，再提出交互改进，最后通过预先定义指标的受控测试验证；针对专业质量风险增加独立复核，不用用户高分替代质量审查。

本次交付能够展示分析产出与方法资产化，但没有提供完整上线实验、收益归因或工时记录，因此不写“满意度提升了多少”“节省了多少工时”或“已完成产品优化闭环”。

## 7. 协作偏好与复盘资产

过程记录体现了几条可落地的协作规则：口径不清时先确认；代码、结果、结论一起交付；每个数值追溯来源；不因异常结果直接修改结论；保留旧版本并记录决策。

公开仓库将这些规则重新整理为 `skills/`、`prompts/` 与 `memory/` 示例。周报代码仅从演示日志生成固定结构的总结，没有实现自动读取真实工作记录，也不声称模型在训练或识别作者的心理人格。
